# テスト設計書

**対象フェーズ：** フェーズ5 — 仕上げ・ローカル動作確認（5.3）  
**テスト実施日：** 2026-06-01  
**テスト環境：** ローカル（Windows 11 / Node.js v24）

---

## 1. テスト対象と目的

| 対象機能                            | テスト目的                                                         |
| ----------------------------------- | ------------------------------------------------------------------ |
| 認証プロキシ（`proxy.ts`）          | 未認証アクセスで HTTP 404 が返ること、ホワイトリストが機能すること |
| `uploads/` ディレクトリ自動生成     | サーバー起動時にディレクトリが存在しなくても自動作成されること     |
| 共通 API 関数（`fetchFromBackend`） | JSON / FormData を自動判別して正しいヘッダーで通信すること         |

---

## 2. テスト環境・前提条件

| 項目               | 値                                                    |
| ------------------ | ----------------------------------------------------- |
| フロントエンド URL | `http://localhost:3001`（Next.js dev）                |
| バックエンド URL   | `http://localhost:4000`（Express / tsx）              |
| データベース       | PostgreSQL（localhost:5432 / portfolio_db）           |
| セッション管理     | Cookie（`session` キー）                              |
| Firebase           | `.env.local` 未設定（ログインフロー検証はスコープ外） |

## 3. テストケース一覧

### 3-A：認証プロキシ（`frontend/proxy.ts`）

| ID   | テスト項目                             | 前提条件                         | テスト手順                                                  | 期待値                                                       | 実測値                                               | 結果 |
| ---- | -------------------------------------- | -------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------- | ---- |
| A-01 | 未認証でダッシュボードにアクセス       | セッション Cookie なし           | `GET /admin/dashboard` を発行                               | HTTP **404**                                                 | 404                                                  | ✅   |
| A-02 | 偽セッションでダッシュボードにアクセス | `session=fake-token` Cookie あり | `GET /admin/dashboard --cookie "session=fake-token"` を発行 | プロキシを通過しページへ進む（今回は Firebase 未設定で 500） | 500（プロキシは通過）                                | ✅   |
| A-03 | ログインページは認証なしでアクセス可能 | セッション Cookie なし           | `GET /admin/login` を発行                                   | プロキシを通過する（404 ではない）                           | 500（Firebase 未設定のページエラー、プロキシは通過） | ✅   |
| A-04 | `/admin` 配下以外はプロキシの対象外    | セッション Cookie なし           | `GET /` を発行                                              | 200（プロキシ不介入）                                        | 200                                                  | ✅   |

**補足**

- A-02・A-03 の 500 はプロキシの挙動ではなく Firebase 環境変数未設定によるページレンダリングエラー。
- Next.js 16 移行に伴い `middleware.ts` → `proxy.ts` へリネーム・関数名を `proxy` に変更（同テスト中に修正済み）。

### 3-B：`uploads/` ディレクトリ自動生成（`backend/src/index.ts`）

| ID   | テスト項目                                       | 前提条件                                 | テスト手順                                           | 期待値                                                               | 実測値                   | 結果 |
| ---- | ------------------------------------------------ | ---------------------------------------- | ---------------------------------------------------- | -------------------------------------------------------------------- | ------------------------ | ---- |
| B-01 | サーバー起動時にディレクトリが存在しない状態     | `backend/public/uploads/` を削除した状態 | `npm run dev` でバックエンドを起動                   | 起動後に `backend/public/uploads/` が自動作成される                  | ディレクトリが生成された | ✅   |
| B-02 | ディレクトリが既に存在する状態でも起動が成功する | `backend/public/uploads/` が存在する状態 | `npm run dev` でバックエンドを起動                   | 上書き・エラーなしで起動完了                                         | 起動成功                 | ✅   |
| B-03 | アップロードしたファイルが正しいパスに保存される | B-01 完了後                              | 後述 C-02 のアップロードを実施し `uploads/` 内を確認 | `backend/public/uploads/{timestamp}-{filename}` にファイルが存在する | ファイルが存在した       | ✅   |

**補足**

- `UPLOADS_DIR` は `path.join(__dirname, "../../public/uploads")` で定義（`backend/src/lib/paths.ts`）。
- `ts-node`（tsx）実行時・コンパイル後のどちらでも同じパスになる。

### 3-C：共通 API 関数 `fetchFromBackend`（`frontend/lib/api/backend.ts`）

| ID   | テスト項目                                                        | 前提条件                                    | テスト手順                                                                                         | 期待値                                                                 | 実測値                                     | 結果 |
| ---- | ----------------------------------------------------------------- | ------------------------------------------- | -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------ | ---- |
| C-01 | JSON ボディの場合に `Content-Type: application/json` が付与される | バックエンド起動済み                        | `fetchFromBackend("/skills", { method:"POST", body: JSON.stringify({...}) })` を実行（スキル登録） | バックエンドが JSON として受け取りレコードを返す                       | `{"id":2,"name":"TypeScript",...}` が返却  | ✅   |
| C-02 | FormData ボディの場合に Content-Type が自動省略される             | バックエンド起動済み                        | `fetchFromBackend("/images", { method:"POST", body: formData })` を実行（画像アップロード）        | multer が multipart を正常受信しレコードを返す                         | `{"id":1,"url":"/uploads/...",...}` が返却 | ✅   |
| C-03 | ボディなし（DELETE）でも正常動作する                              | C-01 で作成したスキルが存在する             | `fetchFromBackend("/skills/2", { method:"DELETE" })` を実行                                        | 削除成功レスポンスが返る                                               | `{"message":"スキルを削除しました"}`       | ✅   |
| C-04 | Next.js rewrite 経由で画像が配信される                            | C-02 でアップロード済みのファイルが存在する | `GET http://localhost:3001/uploads/{filename}` を発行                                              | HTTP 200 でファイルが返る（Express の `/uploads/` 静的配信をプロキシ） | 200                                        | ✅   |

**補足**

- 自動判別のキー：`typeof options.body === "string"` → JSON、それ以外（FormData 等）→ Content-Type を付与しない。
- FormData に手動で `Content-Type` を付けると `boundary` が消えてサーバーがパースできなくなる（意図的に省く設計）。
- `next.config.ts` の `rewrites` で `/uploads/:path*` → `http://localhost:4000/uploads/:path*` にプロキシしている（C-04 で確認）。

## 6. 実行コマンド一覧（再現手順）

```bash
# バックエンド起動
cd backend && npm run dev

# フロントエンド起動
cd frontend && npm run dev

# A-01: 未認証ダッシュボード → 404 確認
curl -s -o /dev/null -w "%{http_code}" http://localhost:3001/admin/dashboard

# C-01: JSON 通信テスト（スキル登録）
curl -s -X POST http://localhost:4000/api/skills \
  -H "Content-Type: application/json" \
  -d '{"name":"TypeScript","level":4,"category":"Language"}'

# C-02: FormData 通信テスト（画像アップロード）
curl -s -X POST http://localhost:4000/api/images \
  -F "file=@/path/to/image.png;type=image/png"

# C-04: Next.js rewrite 経由の画像配信確認
curl -s -o /dev/null -w "%{http_code}" http://localhost:3001/uploads/{filename}
```
